# 出力フォーマットと記述ルール

## Notion貼り付けの前提

生成物はNotionページに貼り付けて使う。そのための制約:

- **チェック項目は `- [ ]` で書く**。Notionではto-doブロックに変換され、そのままチェックを付けて使える
- **入れ子のインデントは半角スペース4つで統一する**。階層がNotion側のネストに対応する
- **セル内改行 (`<br>`) は使わない**。文字列のまま表示されて崩れる
- **チェック項目にテーブルを使わない**。テーブルはセル内で改行できず手順が横に伸びるため、テーブルは冒頭の「対象PR」「テスト前の準備」の2つだけに留める
- 見出し・テーブル・箇条書きはMarkdownのまま貼れば変換される

## 全体テンプレート

````markdown
# リリースQA: <機能名>

## この変更で何ができるようになるか

- <非エンジニアにわかる言葉で3行以内。何が新しくできるか / 何が変わったか>

## 対象PR

| # | PR | タイトル | 主な変更点 |
|---|----|---------|-----------|
| 1 | [#1234](https://github.com/.../pull/1234) | ... | ... |
| 2 | [#1235](https://github.com/.../pull/1235) | ... | ... |

## テスト前の準備

| 項目 | 内容 |
|------|------|
| 環境 | ステージング (https://...) |
| 必要なアカウント | 一般ユーザー / 管理者 / 別テナントのユーザー |
| 事前に用意するデータ | 50MB超のPDF / 空のワークスペース / 100件以上の履歴があるアカウント |
| ブラウザ | Chrome最新 (指定があれば記載) |
| 注意事項 | <データを壊す操作、他の人と共有している環境での注意など> |

## 1. <大項目: 画面・機能の単位>

**共通前提**

- 一般ユーザーでログインしている
- テナントAに所属し、ワークスペースが1つ以上ある

- [ ] 1-1 <確認項目: 結果まで含めた一文>
    - 手順
        - <1行1操作>
        - <1行1操作>
    - 期待する結果
        - <画面上で観測できる事実>

- [ ] 1-2 <確認項目>
    - 前提条件（共通前提から変更）
        - <差し替わる前提だけ>
    - 手順
        - <1行1操作>
    - 期待する結果
        - <画面上で観測できる事実>
        - <副作用があれば別行に>

## 2. <大項目>

**共通前提**

- ...

- [ ] 2-1 <確認項目>
    - 手順
        - ...
    - 期待する結果
        - ...
````

末尾に補足セクション (「時間があれば実施」「開発者に確認を依頼する項目」「リリース作業」) は作らない。成果物はチェック項目だけで構成し、それ以外はチャットでの完了報告に回す。

## 各ブロックの書き方

### チェック項目 (`- [ ]` の行)

先頭に `<大項目番号>-<連番>` を振る (例: `1-1`、`2-3`)。章をまたぐ通し番号にはしない (項目を後から追加しても番号が破綻しないようにするため)。

本文は**結果まで含めた一文**で書く。「〜できる」「〜が表示される」「〜が保存される」の形にする。

| 良い例 | 悪い例 | 悪い理由 |
|--------|--------|---------|
| PDFを1件添付して送信できる | ファイル添付のテスト | 何をもって合格か読み取れない |
| 51MBのファイルはエラーになり添付されない | サイズ上限の確認 | 上限値も期待動作も書かれていない |
| 別テナントのユーザーには一覧に表示されない | 権限チェック | どの画面のどの表示か特定できない |

### 共通前提 (大項目の直下)

- その大項目の**どの項目を実施するときも成り立っていること**だけを書く。ログインするアカウント・権限・組織設定・事前に用意するデータ
- 1つの項目にしか関係しない前提は、ここではなく項目側に書く
- 手順に書ける操作は前提に書かない (ログインは前提、機能の画面を開くのは手順)

### 前提条件 (項目側・差分があるときだけ)

- 共通前提から**差し替わる**ものだけを書き、見出しは `前提条件（共通前提から変更）` にする
- 共通前提に**足す**だけなら `前提条件（追加）` にする
- 差し替えも追加も無い項目には、このブロックを置かない (空の `前提条件` を書かない)

### 手順

- **1行1操作**。`①②③` で1行に連結しない
- 上から順に実行する前提。番号は振らない
- クリックする対象は**画面上の文言をそのまま**カギ括弧で書く (例: 「送信」ボタン、「設定」→「メンバー管理」)
- 画面の入り方から書く。「一覧画面を開く」ではなく「左メニューの「ワークスペース」を開く」のように、初見の人が迷わない起点にする
- 入力する値は**具体的に書く**。「長いタイトルを入力する」ではなく「タイトルに任意の文字を301文字入力する」、プロンプトを送るなら送る文をそのまま書く
- 共通前提で済むことは手順に書かない (ログイン手順を毎項目繰り返さない)

### 期待する結果

- **画面上で観測できる事実**を書く。どこに何がどう表示されるか、どう変化するか
- エラーを期待する項目は、**エラーメッセージの文言**まで書く (実装から拾う)
- 禁止表現: 「正常に動作する」「問題なく表示される」「エラーにならない」だけで終わる書き方
- 副作用は**別の行**に分けて書く (例: 「一覧の先頭に追加される」「件数表示が1増える」)

| 良い例 | 悪い例 |
|--------|--------|
| ファイル名とサイズが入力欄の上に表示され、「送信」ボタンが押せる状態になる | 添付が成功する |
| 「50MBまでのファイルを選択してください」と赤字で表示され、ファイルは添付されない | エラーが出る |
| 一覧が0件のときは「まだ登録がありません」と表示され、表のヘッダーは出ない | 空表示になる |

## 粒度のルール

- **1項目1確認**。「保存できて、一覧にも出て、再読込しても残る」は3項目に割る。**確認内容が別物であるものを1項目に詰めない**というルールで、項目数を稼ぐためのルールではない
- **例外: 同じ境界の内側と外側は1項目にまとめてよい。** 手順が「値を変えて同じ操作をする」だけで、判定が対になっているものが対象
  - 良い例: 「タイトルに300文字は保存でき、301文字は『300文字以内で入力してください』と表示され保存できない」
  - まとめてよい対の例: 上限のちょうど内/外、権限あり/なし、0件/1件の表示
  - まとめては**いけない**例: 「保存できる」と「一覧に出る」(確認対象が別物)、「300文字は保存できる」と「絵文字を含む値は保存できる」(手順も判定も別物)
- 大項目は3〜7個。**1つの大項目の項目は10個までを目安**にし、超える場合は選別で落とすか大項目を分割する
- 同じ操作を値だけ変えて繰り返す項目 (境界値など) は連続して並べ、値の違いが一目でわかるようにする
- 実装用語をどうしても使う必要がある場合 (機能名として画面に出ているものを除く) は、画面から判定できない項目である可能性が高い。項目にせず完了報告に回す

## 冗長さを避ける

同じ確認を言い換えただけの項目が並ぶと、量だけ増えて実施の質が下がる。生成後に次の重複パターンを潰す。

| 重複パターン | 対処 |
|-------------|------|
| 同じ入力欄に対する「空」「スペースのみ」「未選択」が別項目になっている | 未入力系は1項目にまとめる |
| 複数の入力欄それぞれに同じ文字種チェック (絵文字・記号) を並べている | 代表1箇所に絞り、他は落とす |
| 画面ごとに同じレスポンシブ確認を繰り返している | 変更が入った画面のうち代表1〜2画面に絞る |
| 正常系の項目が、操作の入り口 (メニュー経由 / URL直打ち / ボタン経由) ごとに割れている | 主要な入り口1つに絞る |
