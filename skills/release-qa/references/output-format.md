# 出力フォーマットと記述ルール

## 基本形

実際のユースケースを大項目にし、その達成に必要な重要な通過点だけを子チェックにする。`前提条件`、`手順`、`期待する結果` の定型ブロックや項目番号は使わない。

````markdown
# リリースQA: <ユーザーから見た変更名>

対象PR: [#1234](https://github.com/.../pull/1234)

## テスト前準備

- <共通して必要なアカウント・権限>
- <実際に使う入力ファイルや事前データ>
- <全項目に共通する開始画面や操作>

## QAチェックリスト

- [ ] <ユーザーが達成する仕事>
    - [ ] <入力して実行すると、意図した処理経路が画面上で確認できる>
        - 「<そのままコピーして送信できるプロンプト>」
    - [ ] <必要な成果物が表示・ダウンロード・利用できる>
    - [ ] <成果物の重要な値や内容が入力と一致する>

- [ ] <別のユーザーの仕事>
    - [ ] <このシナリオ固有の重要な通過点>
    - [ ] <最終成果物と内容の合格条件>

- [ ] <複数シナリオに共通する横断的な挙動>
    - [ ] <再読み込みや再訪問後も、必要な状態と成果物を利用できる>
````

## 大項目

大項目は、ユーザーが実際に達成する仕事を短い動詞句で書く。

| 良い例 | 悪い例 | 悪い理由 |
|--------|--------|---------|
| 売上分析の結果からグラフを作成 | CSVファイルの確認 | ユーザーの最終目的ではない |
| 予算Excelからレポートを作成 | Excel編集モードの確認 | 実装・機能単位になっている |
| 生成画像を使ってスライドを作成 | 画像、タイトル、PDFを確認 | 1つの仕事を観測箇所ごとに分割している |

- 1つの大項目で、開始から最終成果物までを通す
- 同じユーザー目的で入力値や入口だけが違うケースを増やさない
- 独立した主要な利用経路だけを別の大項目にする
- 複数シナリオに共通する履歴保持・再利用・権限確認は、最後に1つの横断項目へまとめる

## 子チェック

子チェックは、大項目のシナリオが壊れていないと判断するための重要な通過点だけを書く。原則2〜4件にする。

優先する通過点:

- 意図した機能・処理先・モードが使われたことを画面上で確認できる
- 中間成果物と最終成果物が表示され、開く・ダウンロード・再利用できる
- 入力から導ける重要な値、文言、画像、件数が成果物間で一致する
- 保存・履歴・権限など、今回の変更で壊れ得る横断的な状態が保たれる

チェックボックスの文中に操作と合格結果をまとめる。

| 良い例 | 悪い例 | 悪い理由 |
|--------|--------|---------|
| `monthly_sales.csv` を添付してプロンプトを送信すると、「売上分析」が表示される | CSVを添付する | 合格結果がない |
| `sales_analysis.csv`、`findings.md`、`sales_trend.png` が表示・ダウンロードできる | 生成ファイルを1件ずつ確認する | 1つの成果をファイルごとに分割している |
| 分析結果に「最高売上は4月の180」が含まれ、グラフがCSVの値と一致する | 出力内容を細かく確認する | 判定基準がない |

処理経路・成果物・内容の3つが同じシナリオで重要なら、それぞれを子チェックにする。画面の全表示や操作手順を子チェックへ変換しない。

## プロンプト・入力値

- QA担当者がそのままコピーして使える完全な文を書く
- プロンプトは、それを送信する子チェックの直下へ通常の箇条書きとして置く
- ファイル名、入力値、期待する数値・文言を具体的にする
- 再現性が必要な場合は、自由回答ではなく検算できるデータと期待値を使う
- 実際の利用では不自然な入力を、コード経路を通すためだけに作らない

## テスト前準備

- 全シナリオに共通する準備だけを書く
- アカウント、権限、機能設定、入力ファイル、共通の開始画面を箇条書きにする
- 特定のシナリオだけに必要な入力は、その大項目の最初の子チェックへ含める
- ブラウザや端末は、その環境に固有のバグ仮説がある場合だけ指定する

## 簡潔さの基準

- 大項目1件につき子チェックは原則2〜4件にする
- 1回の操作で同時に得られる成果物を別項目に分割しない
- 同じ合否を示す表示箇所を複数確認しない
- ファイルの表示とダウンロードは、一連の利用可否として1つにまとめてよい
- 保存直後・一覧表示・再読み込み後は、永続化がリスクなら1つの横断項目にまとめる
- 内部のバグ仮説、diff、関数名、API名を成果物へ書かない
- 末尾に「時間があれば実施」「開発者に確認を依頼する項目」「リリース作業」を置かない
