# 出力フォーマットと記述ルール

## Notion貼り付けの前提

生成物はNotionページに貼り付けて使う。そのための制約:

- **テーブルのセル内では `- [ ]` がチェックボックスにならない**。チェック欄は1列目の `☐` 文字で表現し、実施時にテキストを `☑` に書き換えて使う
- **セル内改行 (`<br>`) は使わない**。Notionで文字列のまま表示されて崩れる。複数ステップは `①②③` で1行に連結する
- 見出し・テーブル・箇条書きはMarkdownのまま貼れば変換される。3列以上のテーブルは横幅が窮屈になるので、1セルの文が長くなりすぎないようにする

## 全体テンプレート

````markdown
# リリースQA: <機能名>

## この変更で何ができるようになるか

- <非エンジニアにわかる言葉で3行以内。何が新しくできるか / 何が変わったか>

## 対象PR

| # | PR | タイトル | 主な変更点 |
|---|----|---------|-----------|
| 1 | [#1234](https://github.com/.../pull/1234) | ... | ... |
| 2 | [#1235](https://github.com/.../pull/1235) | ... | ... |

## テスト前の準備

| 項目 | 内容 |
|------|------|
| 環境 | ステージング (https://...) |
| 必要なアカウント | 一般ユーザー / 管理者 / 別テナントのユーザー |
| 事前に用意するデータ | 50MB超のPDF / 空のワークスペース / 100件以上の履歴があるアカウント |
| ブラウザ | Chrome最新 (指定があれば記載) |
| 注意事項 | <データを壊す操作、他の人と共有している環境での注意など> |

## 1. <大項目: 画面・機能の単位>

**前提**: 一般ユーザーでログイン / テナントA / ワークスペースが1つ以上ある状態

| ✓ | # | 確認項目 | 再現手順 | 想定事象 |
|---|---|---------|---------|---------|
| ☐ | 1-1 | ... | ... | ... |
| ☐ | 1-2 | ... | ... | ... |

## 2. <大項目>

**前提**: ...

| ✓ | # | 確認項目 | 再現手順 | 想定事象 |
|---|---|---------|---------|---------|
| ☐ | 2-1 | ... | ... | ... |

## 時間があれば実施

必須ではないが、余裕があれば確認したい項目。影響度と発生確率がどちらも低いと判断したもの。

| ✓ | # | 確認項目 | 再現手順 | 想定事象 |
|---|---|---------|---------|---------|
| ☐ | A-1 | ... | ... | ... |

## 開発者に確認を依頼する項目

画面からは合否を判定できないもの。担当エンジニアに確認を依頼する。

| ✓ | # | 確認内容 | 確認方法 |
|---|---|---------|---------|
| ☐ | D-1 | 既存データの移行が完了しているか | リリース後にログまたはDBで確認 |

## リリース時・リリース後の作業

| ✓ | # | 作業内容 | タイミング |
|---|---|---------|-----------|
| ☐ | R-1 | 環境変数 <名前> の追加 | デプロイ前 |
````

## 各列の書き方

### `✓` 列

常に `☐`。実施時にQA担当者が `☑` に書き換える。

### `#` 列

`<大項目番号>-<連番>` (例: `1-1`、`2-3`)。「時間があれば実施」は `A-1`、開発者に確認を依頼する項目は `D-1`、リリース作業は `R-1` と接頭辞で区別する。項目を後から追加しても番号が破綻しないよう、章をまたぐ通し番号にはしない。

### `確認項目` 列

**結果まで含めた一文**で書く。「〜できる」「〜が表示される」「〜が保存される」の形にする。

| 良い例 | 悪い例 | 悪い理由 |
|--------|--------|---------|
| PDFを1件添付して送信できる | ファイル添付のテスト | 何をもって合格か読み取れない |
| 51MBのファイルはエラーになり添付されない | サイズ上限の確認 | 上限値も期待動作も書かれていない |
| 別テナントのユーザーには一覧に表示されない | 権限チェック | どの画面のどの表示か特定できない |

### `再現手順` 列

- `①②③` で番号を振り、1行に連結する
- クリックする対象は**画面上の文言をそのまま**カギ括弧で書く (例: 「送信」ボタン、「設定」→「メンバー管理」)
- 画面の入り方から書く。「一覧画面を開く」ではなく「①左メニューの「ワークスペース」を開く」のように、初見の人が迷わない起点にする
- 前提で済むことは手順に書かない (ログイン手順を毎行繰り返さない)

### `想定事象` 列

- **画面上で観測できる事実**を書く。どこに何がどう表示されるか、どう変化するか
- エラーを期待する項目は、**エラーメッセージの文言**まで書く (実装から拾う)
- 禁止表現: 「正常に動作する」「問題なく表示される」「エラーにならない」だけで終わる書き方
- 副作用があるなら併記する (例: 「一覧の先頭に追加され、件数表示が1増える」)

| 良い例 | 悪い例 |
|--------|--------|
| ファイル名とサイズが入力欄の上に表示され、「送信」ボタンが押せる状態になる | 添付が成功する |
| 「50MBまでのファイルを選択してください」と赤字で表示され、ファイルは添付されない | エラーが出る |
| 一覧が0件のときは「まだ登録がありません」と表示され、表のヘッダーは出ない | 空表示になる |

## 粒度のルール

- **1項目1確認**。「保存できて、一覧にも出て、再読込しても残る」は3項目に割る。**確認内容が別物であるものを1行に詰めない**というルールで、行数を稼ぐためのルールではない
- **例外: 同じ境界の内側と外側は1項目にまとめてよい。** 手順が「値を変えて同じ操作をする」だけで、判定が対になっているものが対象
  - 良い例: 「タイトルに300文字は保存でき、301文字は『300文字以内で入力してください』と表示され保存できない」
  - まとめてよい対の例: 上限のちょうど内/外、権限あり/なし、0件/1件の表示
  - まとめては**いけない**例: 「保存できる」と「一覧に出る」(確認対象が別物)、「300文字は保存できる」と「絵文字を含む値は保存できる」(手順も判定も別物)
- 大項目は3〜7個。**1つの大項目の小項目は10個までを目安**にし、超える場合は選別で任意に回すか大項目を分割する
- 同じ操作を値だけ変えて繰り返す項目 (境界値など) は連続して並べ、値の違いが一目でわかるようにする
- 実装用語をどうしても使う必要がある場合 (機能名として画面に出ているものを除く) は、その項目自体が開発者確認向けである可能性が高い。末尾のセクションに移す

## 冗長さを避ける

同じ確認を言い換えただけの項目が並ぶと、量だけ増えて実施の質が下がる。生成後に次の重複パターンを潰す。

| 重複パターン | 対処 |
|-------------|------|
| 同じ入力欄に対する「空」「スペースのみ」「未選択」が別項目になっている | 未入力系は1項目にまとめる |
| 複数の入力欄それぞれに同じ文字種チェック (絵文字・記号) を並べている | 代表1箇所に絞り、他は任意へ回す |
| 画面ごとに同じレスポンシブ確認を繰り返している | 変更が入った画面のうち代表1〜2画面に絞る |
| 正常系の項目が、操作の入り口 (メニュー経由 / URL直打ち / ボタン経由) ごとに割れている | 主要な入り口1つを必須にし、残りは任意へ回す |
