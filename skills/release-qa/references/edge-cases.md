# バグ仮説を補う境界値・コーナーケースのカタログ

実装が**暗黙に仮定していること**を見つけ、その仮定を破るとユーザー影響のあるバグになる箇所を探すための手順書。

これはテストケースの網羅表ではない。ここで挙げる値や操作は、具体的なバグ仮説を作るための材料であり、そのままQA項目へ変換しない。どれを残すかはSKILL.mdの選別工程で決める。

**カテゴリを機械的に全部当てない。** 各カテゴリの「diffで探すサイン」が実際に現れ、かつ壊れた場合のユーザー影響を説明できるカテゴリだけを使う。サインがない、または影響が軽いカテゴリは飛ばす。

**開発者の気になるポイントと高リスクな変更の周辺から先に当てる。** 同じ原因で壊れる値は代表値1つに絞り、境界の内外は必要なら1項目にまとめる。

**候補は実際のユースケースに組み込む。** 境界値や異常操作を単独の大項目にせず、ユーザーが現実に行う一連の仕事の入力・状態として使う。実際のユースケースでは検出できず、影響度が高い場合だけ独立項目にする。

## 候補を増やしすぎないルール

- 1つの条件分岐には、誤りを最も検出しやすい境界または状態を選ぶ
- 同じバリデーション経路を通る空文字・空白・未選択を別項目にしない
- 同じ原因で壊れる文字種、件数、端末、操作入口を総当たりしない
- 正常系は主要フローのスモークテストで確認し、各カテゴリに正常系を作らない
- 「起きたら困る」だけで、今回の変更から起きる理由を説明できないケースは作らない
- 現実の利用では不自然な値を、境界値カタログにあるという理由だけで使わない

## 出発点となる6つの問い

手順3で特定した高リスクな影響経路にこの問いを当てる。「仮定している」と答え、かつ破ったときのユーザー影響を説明できる場合だけ候補にする。

1. この入力は**必ず存在する**と仮定していないか (空・未入力・未選択)
2. このリスト・配列は**空ではない**と仮定していないか (0件・1件・大量)
3. この操作は**1回だけ**行われると仮定していないか (連打・二重送信・リロード)
4. この処理は**成功する**と仮定していないか (通信失敗・タイムアウト・権限エラー)
5. この値は**最新**だと仮定していないか (別タブで更新済み・削除済み・権限変更後)
6. ユーザーは**画面の順序どおりに**操作すると仮定していないか (ブラウザバック・URL直打ち・途中離脱)

## カテゴリ別の探し方

### 1. 入力値の境界

**diffで探すサイン**: `maxLength` / `min` / `max` / 正規表現 / `required` / 文字数カウント / 数値の定数 / 型変換

**仮説の材料**:

- 上限のちょうど内側 (上限と同じ値) と外側 (上限+1) の両方
- 空文字・スペースのみ・前後にスペースを含む値 (トリムされるか)
- 絵文字・サロゲートペア (𩸽 など)・改行を含む複数行テキスト
- 半角/全角の混在、記号 (`<script>`・`&`・`"`・`|`・`/`) を含む値 — 表示が崩れないか、そのまま文字として表示されるか
- 数値項目に `0`・マイナス値・小数・非常に大きい値・数字以外の文字
- 日付項目に過去日・未来日・存在しない日付 (2/30)・開始日 > 終了日

> 例: 上限判定が変更されたなら「タイトルに300文字は保存でき、301文字は保存されずエラーが表示される」を1項目にする。空白は同じ原因を検出するなら追加しない。

### 2. 件数・量の境界

**diffで探すサイン**: 一覧・ページネーション・ソート・`limit` / `offset` / `slice` / 集計 / 空配列の分岐

**仮説の材料**:

- 0件のとき (空状態の文言が出るか、ヘッダーやボタンが壊れないか)
- 1件だけのとき (「n件」の表示、区切り線、並び替えが機能するか)
- ページの境界 (1ページ目の末尾と2ページ目の先頭で重複・欠落がないか)
- 大量データ (数百〜数千件) で表示が終わるか、スクロールや検索が実用的か
- 一覧の先頭・末尾の要素に対する操作 (削除・並び替え・上下移動)

> 例: 「一覧が0件のときは『まだ登録がありません』と表示され、並び替えボタンは押せない」「21件目以降が2ページ目に表示され、1ページ目と重複しない」

### 3. 状態遷移とタイミング

**diffで探すサイン**: `async` / `await` / ローディング状態 / `disabled` の制御 / ステータスを持つデータ / ポーリング / WebSocket / ジョブ投入

**仮説の材料**:

- 処理中に同じボタンを連打する (二重登録されないか、ボタンが押せなくなるか)
- 処理中に画面をリロードする / 別画面へ移動して戻る (状態が正しく復元されるか、処理は続いているか)
- 処理中に対象データを別画面から削除する
- 完了通知が出る前に次の操作を始める
- ブラウザの戻る/進むで前の画面に戻ってから操作する
- 長時間放置してセッションが切れた状態で操作する (ログイン画面に戻るか、エラーで固まらないか)

> 例: 「送信ボタンを素早く3回押しても、メッセージは1件しか作成されない」「アップロード中にリロードしても、完了済みのファイルは一覧に残っている」

### 4. 権限・テナントの境界

**diffで探すサイン**: ロール判定 / 権限チェック / テナントID・組織IDの絞り込み / 認可のミドルウェア / 画面の出し分け

**仮説の材料**:

- 権限のないロールで、その機能のボタン・メニューが表示されないこと
- 権限のないロールで、URLを直接開いた場合にエラーまたは一覧へ戻されること (表示が隠れているだけでないか)
- 別テナントのユーザーで、他テナントのデータが一覧・検索・詳細に出てこないこと
- 自分が作成していないデータに対する編集・削除ができないこと
- 操作中に権限を剥奪された場合の挙動

> 例: 「閲覧のみのユーザーには『編集』ボタンが表示されない」「閲覧のみのユーザーが編集画面のURLを直接開くと、権限がない旨のメッセージが表示され一覧に戻る」

### 5. 既存データ・データの欠損

**diffで探すサイン**: マイグレーション / 新しく追加されたフィールド / デフォルト値 / `Optional` / null許容 / 既定値の設定

**仮説の材料**:

- **リリース前に作られた古いデータ**を開く (新項目が未設定でも画面が壊れないか、初期値が妥当か)
- 任意項目を空のまま保存して、詳細・一覧・編集画面で表示が崩れないこと
- 関連データが削除済みのレコードを表示・編集する
- 作成 → 更新 → 削除の一連の流れで、関連する表示 (件数・履歴・通知) が整合すること

> 例: 「この機能が入る前に作成したワークスペースを開いても、新しい設定欄が『未設定』と表示され、保存できる」

### 6. 通信・外部依存の失敗

**diffで探すサイン**: 外部APIの呼び出し / リトライ / タイムアウト / ファイルアップロード / ストレージ / エラーハンドリングの分岐

**仮説の材料**:

- 通信が遅い状態での操作 (ブラウザの開発者ツールでネットワークを絞る、または大きいファイルを使う)
- 途中で通信が切れた場合 (機内モードにする)、エラーが表示され、復帰後に再実行できること
- サイズの大きいファイル・想定外の拡張子・拡張子だけ偽装したファイル
- 同名ファイルを再アップロードした場合の挙動

> 例: 「アップロード中に通信を切ると『通信に失敗しました』と表示され、通信復帰後に同じファイルを再アップロードできる」

### 7. 表示・環境

**diffで探すサイン**: CSS・レイアウト・i18nの辞書追加 / 文字列の連結 / 日付や数値のフォーマット / 条件付きレンダリング

**仮説の材料**:

- 極端に長い名前・タイトル (100文字以上) を入れたときのレイアウト崩れ・省略表示
- 日本語/英語の切り替えで、追加された文言がすべて翻訳されていること (英語のまま残っていないか)
- スマートフォン幅・タブレット幅での表示 (ボタンが押せるか、テーブルが横スクロールするか)
- ローディング表示・エラー表示・空状態の3つが、それぞれ意図通り出ること

> 例: 「表示名に100文字入力しても一覧のレイアウトが崩れず、末尾が「…」で省略される」

### 8. 並行操作

**diffで探すサイン**: 更新処理 / 楽観ロック / バージョン番号 / キャッシュ / 一覧の再取得

**仮説の材料**:

- 2つのタブで同じデータを開き、片方で編集・保存した後にもう片方で保存する
- 2つのタブで同じデータを開き、片方で削除した後にもう片方で開く・編集する
- 一覧を開いたまま別タブでデータを追加し、元のタブで再読込せずに操作する

> 例: 「タブAとタブBで同じ設定画面を開き、Aで保存した後にBで保存すると、内容が上書きされるか警告が出る (どちらが正しいかは選別工程でユーザーに確認して確定させる)」

## 仕上げ: バリデーションの欠落を探す

上のカテゴリを当てた後、**逆向き**に探す。ここが未想定ケースの本命。

1. diffの中の入力経路（フォーム・パラメータ・ファイル選択・URLのクエリ）を列挙する
2. それぞれにバリデーションが**書かれているか**を確認する
3. 書かれていない経路から不正値が変更箇所へ到達するか確認する
4. 到達した場合にデータ不整合、権限漏れ、主要フロー停止などが起き得るときだけ候補にする
5. 同じ欠落を検出できる値が複数ある場合は、最も再現しやすい代表値を1つ選ぶ

ここで見つかったものは、ユーザー影響が大きい場合に選別工程で優先する。入力経路ごとの総当たりにはしない。

期待動作が実装から読み取れない場合は、影響度が高い候補だけユーザーに確認する。影響度が低い候補は質問や項目を増やさず落とす。確認しても確定しなければ、チェックリストには載せず残存リスクとして報告する。
