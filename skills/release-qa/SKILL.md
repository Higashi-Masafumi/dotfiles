# Release QA

## 目的

**開発者が気にしているポイントを骨格にし**、PRのdiffで裏取りと抜け漏れ検出をしながら、**このQAを初めて見る非エンジニアがそのまま実施できる**チェックリストを作る。満たすべき条件は5つで、どれか1つでも欠けたら未完成とみなす。

1. **初見でわかる**: 実装用語 (API名・関数名・DBカラム名・変数名) がゼロで、画面上のラベルと操作だけで書かれている
2. **手順と期待する結果が全項目にある**: 手順どおり操作すれば、誰がやっても同じ合否判定にたどり着く
3. **実装者が想定していないケースを含む**: 境界値・コーナーケースをdiffから能動的に導出する。正常系の確認だけで終わらせない
4. **的外れな項目・自明に担保されている項目が無い**: 全項目が、開発者の気になるポイントか今回のdiffの変更箇所のどちらかに紐づいている。「一応書いておいた」項目が1つでも混ざると、QA担当者はリスト全体を信用しなくなる
5. **実施しきれる量に収まっている**: リスクの高い順に絞り、変更規模に見合った量にする。**網羅性と簡潔さは両立させる** — 候補を全部並べたリストは、結果として全項目が雑に流されるので条件3も満たせない

## 入力

`$ARGUMENTS` にGitHubのPR URLをスペース区切りまたは改行区切りで受け取る。気になるポイントが一緒に書かれていればそれも使う。

```
/release-qa https://github.com/neoAI-inc/neo-smart-chat/pull/1234 https://github.com/neoAI-inc/neo-smart-chat/pull/1235
```

PR URLは必須。1つも渡されなかった場合は実行前にユーザーに確認する。

## 手順

### 1. 気になるポイントのヒアリング (最初にやる)

**この工程を飛ばして生成に進まない。** 開発者が何を心配しているかが分からないまま作ると、diffの表面をなぞった的外れなリストになる (条件4が落ちる)。

`$ARGUMENTS` に気になるポイントが書かれていなければ、次を**まとめて1回で**ユーザーに質問し、回答を待つ。

- 今回のリリースで**特に確認したい挙動**は何か (「ここが動けばOK」と言える主要フロー)
- **壊れそう / 自信がない箇所**はどこか (実装中に迷った分岐、他機能への影響が読めない箇所)
- 触った範囲のうち、**QAに触ってほしくない部分**があるか (別チームの担当、フラグで未公開の機能など)
- QA担当者が用意できる**アカウント・権限・テスト環境**の制約 (別テナントのアカウントを作れるか、管理者権限を渡せるか、通信を絞るような操作を頼めるか)

回答は箇条書きの断片で十分。**完璧な回答を求めて何度も往復しない。** 1回聞いて返ってきた内容を骨格にする。手順2のdiff取得はこの質問と並行して走らせてよい。

### 2. diffとPR情報の取得

同梱の `scripts/fetch_pr_diffs.py` (このSKILL.mdと同じディレクトリにある) で、各PRのメタデータ (タイトル・説明・変更ファイル数など) とdiffをまとめて取得する。インストール先はホストによって異なるので、パスはこのSKILL.mdの場所を基準に解決する。

```bash
python3 <このスキルのディレクトリ>/scripts/fetch_pr_diffs.py <PR URL...>
```

`gh` の認証が済んでいない環境では動かないので、失敗したら `gh auth status` を確認するようユーザーに伝える。

- 各URLから owner/repo/PR番号を都度パースするため、対象PRが別リポジトリにまたがっていても動作する
- 出力は一時ディレクトリに `<owner>__<repo>__<number>.md` として保存される (メタデータ + description + diff)
- 取得できなかったPR (権限不足・存在しない・URL不正) は標準エラーに出るので、続行前にユーザーと共有する

### 3. 変更内容の把握と気になるポイントの突合

- 出力された各PRのmdファイルを読み、title/descriptionから意図を、diffから実際の変更内容を把握する
- PRが3件以上ある場合は、サブエージェントで各PRを並列に読み込み・要約させ、メインのcontextを圧迫しないようにする
- 対象リポジトリがローカルにある場合は、diffだけでは判断できない箇所 (変更された関数の呼び出し元、既存のバリデーション、画面上のラベル文言) を実際のソースで確認する。**画面ラベルの正確な文言はチェックリストの品質に直結する**ため、フロントエンドのコードやi18nの辞書ファイルから実際の表示文字列を拾う

把握したうえで、手順1の気になるポイントと突き合わせて次の2つに仕分ける。ここが後段の選別の材料になる。

- **気になるポイント → diffのどこか**: 対応するコードが見つかれば、その周辺の条件分岐から具体的な確認値を作れる。見つからなければ、開発者が心配しているのに変更が入っていないという情報なので、手順7でユーザーに確認する
- **diffのうち気になるポイントで触れられていない変更**: 影響度が高そうなものだけを候補に残し、手順7で「追加すべきか」をユーザーに質問する。勝手に項目を足さない

### 4. ユーザーから見える挙動変化への翻訳

diffの変更を、**QA担当者が画面上で観測できる事実**に置き換える。

- フロントエンドの変更 → どの画面のどの表示・操作がどう変わるか
- バックエンドのみの変更 → レスポンス内容・エラーメッセージ・処理速度・保存されるデータなど、ユーザーから見て何が変わるか。「画面に変化がない」と結論づける前に、エラー時の表示や一覧の並び順など間接的に見える箇所を疑う
- 設定・環境変数・マイグレーションの変更 → 既存データがどう見えるか。リリース作業そのものはチェックリストに載せず、手順10の報告で伝える

ここで翻訳できなかった変更 (画面から一切観測できないもの) は項目にせず、手順10の報告に回す。

### 5. 大項目 (テスト観点のグルーピング) を決める

画面・機能の単位で大項目を切る。PRごとには**分けない**。目安は3〜7個。**気になるポイントで挙がったものを優先して大項目にし**、残りは以下の観点のうち**今回のdiffが実際に触っているものだけ**を足す。触っていない観点の大項目は作らない。

- 変更された機能そのものの正常系
- 変更された機能の異常系・境界値
- 権限・テナント (ロール違い、他テナントのデータが見えないか)
- 既存機能への影響 (リグレッション)
- 表示・i18n (日英切り替え、表示崩れ、ローディング/エラー表示、レスポンシブ)
- データの整合性 (作成・更新・削除に伴う関連データの状態)

例: diffにロール判定・テナント絞り込みが一切ないなら「権限・テナント」の大項目は作らない。i18nの辞書に手が入っていないなら「表示・i18n」を独立した大項目にはせず、表示崩れの項目だけを他の大項目に混ぜる。

大項目を切ったら、その大項目の全項目に共通する前提 (ログインするアカウント・権限・組織設定・事前データ) を1つにまとめる。これが出力の **共通前提** になる。

### 6. 境界値・コーナーケースの候補出し

**この工程を省略しない。** 同梱の `references/edge-cases.md` を読んで候補を洗い出す。ただし**全カテゴリを機械的に当てるのではなく、diffにそのカテゴリの「探すサイン」が実際に現れているかを先に判定し、現れたカテゴリだけを当てる**。

- 気になるポイントの周辺 (対応するコードの近く) から先に当てる。開発者が心配している箇所の境界値が、最も価値の高い項目になる
- サインが1つも見つからないカテゴリはそのまま飛ばす (例: 外部API呼び出しもファイルアップロードもdiffに無いなら「通信・外部依存の失敗」は当てない)
- 判定に迷ったら当てる側に倒す。ここは候補出しの工程で、絞るのは次の工程の役割

特に重視するのは次の2つの探し方:

- **境界のちょうど内と外**: diffの条件分岐 (`if`・early return・バリデーション・上限値の定数) を見つけたら、その境界の内側と外側の両方を候補にする
- **バリデーションが無い入力経路**: バリデーションが**書かれていない**入力・操作経路を探す。ここが「実装段階で想定されていないケース」の本命なので、見つけたら必ず候補にする

### 7. 選別 (残す / 落とす / ユーザーに確認する)

**候補をそのまま全部出さない。** 量が多いとQA担当者が実施しきれず全項目が雑に流される。それ以上に、**紐づけの弱い項目が混ざるとリスト全体が信用されなくなる**。

#### 項目数の目安

手順2で取得した各PRのメタデータ行 (`Changed files: N (+A/-D)`) を全PRで合計して規模を決める。テストコード・lockファイル・自動生成物は行数から除く。

| 規模 | 目安 | 項目数 |
|------|------|-------|
| 小 | 変更5ファイル以下 / 増減200行未満 | 15項目前後 |
| 中 | 変更20ファイル以下 / 増減1000行未満 | 25項目前後 |
| 大 | それ以上 | 40項目を**上限** |

#### 残す基準

各候補に「**壊れたときの影響度**」と「**実際に踏まれる確率**」を当て、高いものから残す。上限に達したら残りは落とす。

- **影響度が高い**: データが失われる / 他人・他テナントのデータが見える / 課金・外部通知が誤る / 機能そのものが使えなくなる
- **確率が高い**: 主要な操作フロー上にある / 全ユーザーが通る / 自由記述の入力欄である

上限に関係なく残すもの:

- **気になるポイントに挙がった観点** (開発者が心配している以上、外さない)
- 変更された機能の**主要フローの正常系** (これが通らないならリリースできない)
- **権限・テナント境界**の項目 (diffに該当のサインがある場合)
- **データの破壊・不整合**につながる項目 (削除・マイグレーション・一括更新)

これらを入れて上限を超えるなら、上限ではなくこちらを優先する。超えた分は正常系の派生パターン (同じ操作を別の入り口から行う等) から落とす。

#### 落とす基準

次のどれかに当てはまる候補は、リスクが高そうに見えても**載せない**。

- **今回のdiffのどの変更が原因で落ちるかを指せない** — 変更と無関係なリグレッション確認。「念のため」で入れた項目はここで全部落ちる
- **フレームワーク・プラットフォーム・既存の共通処理が保証している** — ログインできること、通信が暗号化されること、共通コンポーネントが既に担保している必須入力チェック、ブラウザ標準の入力制御
- **diffが触っておらず、変更前から同じ挙動** — 既存バグの掘り起こしはこのQAの目的ではない。気づいたら成果物ではなく手順10の報告で伝える
- **QA担当者が手順を実行できない** — 開発者ツールでの通信制御、DBの直接確認、複数テナントのアカウント発行など、手順1で「用意できない」と回答があったもの
- **期待する結果が確定できない** — 下の確認でユーザーに聞いて確定させる。確定できなければ落とす (判定できない項目はQA担当者を止めるだけ)

判定に迷ったら、**その項目が落ちたときに開発者が驚くか**で決める。驚かない (当然通ると思っている) なら落とす。

#### ユーザーに確認する

選別の結果、次に当てはまるものが出たらユーザー (= 開発者) に**まとめて1回で**質問し、回答を反映してから生成に進む。

- diffに変更があるのに気になるポイントで触れられていない箇所が、影響度の高い候補になった → **この観点を追加すべきか**を聞く
- 期待する結果が実装から読み取れない → **どうなるのが正しいか**を聞く
- 影響度は高いが、手順1で聞いた環境制約では実施できない → **環境を用意できるか / 開発者側で確認するか**を聞く

質問しても確定しなかったものは落とし、手順10の報告で列挙する。

### 8. チェックリストの生成

`references/output-format.md` のテンプレートと記述ルールに従って生成する。要点:

- 大項目は `##` 見出し、その直下に **共通前提** を箇条書きで書く
- 小項目は `- [ ]` のチェックボックス1行 + 入れ子の `前提条件` (差分があるときだけ) / `手順` / `期待する結果`
- 手順は**1行1操作**。1行に連結しない
- 冒頭に「この変更で何ができるようになるか」「対象PR一覧」「テスト前の準備」を置く
- 末尾に補足セクションは作らない。チェック項目だけの構成にする

### 9. 自己レビュー (品質ゲート)

生成したチェックリストを読み返し、以下をすべて満たすまで直す。

- [ ] 各項目が「気になるポイント」か「diffの具体的な変更」のどちらかに紐づいている (紐づけを言葉で説明できない項目は落とす)
- [ ] 実装用語 (API名・関数名・カラム名・変数名・PR番号) が項目の本文に残っていない
- [ ] 「正常に動作する」「問題なく表示される」のような判定できない期待する結果がない
- [ ] 1項目に複数の**別々の**確認が詰め込まれていない (同じ境界の内側と外側を1項目にまとめたものは除く)
- [ ] 手順の1行が1操作になっている (`①②③` のような1行連結が残っていない)
- [ ] ボタン名・メニュー名が実際の画面文言と一致している (推測で書いた箇所が残っていないか)
- [ ] 共通前提と各項目の前提条件を読めば、QA担当者が自力でテスト環境を準備できる
- [ ] 境界値・コーナーケースが含まれている (正常系だけになっていない)

### 10. 保存と報告

- プロジェクトルートに `release-qa/` ディレクトリがなければ作成する
- `.gitignore` に `release-qa/` が含まれていなければ追記する (誤ってコミットされないようにするため)
- `release-qa/<日付>-<機能名スラッグ>.md` として保存する (例: `release-qa/2026-08-04-workspace-file-upload.md`)

保存後、ユーザーに次を報告する。成果物に載せなかった情報はここで渡しきる。

- ファイルパスと、大項目ごとの項目数・判定した規模
- **落とした候補とその理由** (特に「環境が用意できない」「期待動作が確定しなかった」で落ちたもの)
- **開発者側で確認が必要な事項** (画面から観測できない変更、ログやDBでしか確認できないもの)
- **リリース時・リリース後に必要な作業** (環境変数の追加、マイグレーション、フラグの切り替えなど)
- diffを読む過程で気づいた**既存バグらしき挙動** (今回のQA対象外として)
