# Release QA

## 目的

指定された一連のPR (基本的に同一機能に関する複数PR) の差分をすべて読み、**このQAを初めて見る非エンジニアがそのまま実施できる**チェックリストを作る。満たすべき条件は4つで、どれか1つでも欠けたら未完成とみなす。

1. **初見でわかる**: 実装用語 (API名・関数名・DBカラム名・変数名) がゼロで、画面上のラベルと操作だけで書かれている
2. **再現手順と想定事象が全項目にある**: 手順どおり操作すれば、誰がやっても同じ合否判定にたどり着く
3. **実装者が想定していないケースを含む**: 境界値・コーナーケースをdiffから能動的に導出する。正常系の確認だけで終わらせない
4. **実施しきれる量に収まっている**: リスクの高い順に必須項目を絞り、変更規模に見合った量にする。**網羅性と簡潔さは両立させる** — 候補を全部並べたリストは、結果として全項目が雑に流されるので条件3も満たせない

## 入力

`$ARGUMENTS` にGitHubのPR URLをスペース区切りまたは改行区切りで受け取る。

```
/release-qa https://github.com/neoAI-inc/neo-smart-chat/pull/1234 https://github.com/neoAI-inc/neo-smart-chat/pull/1235
```

PR URLが1つも渡されなかった場合は、実行前にユーザーに確認する。

## 手順

### 1. diffとPR情報の取得

同梱の `scripts/fetch_pr_diffs.py` (このSKILL.mdと同じディレクトリにある) で、各PRのメタデータ (タイトル・説明・変更ファイル数など) とdiffをまとめて取得する。インストール先はホストによって異なるので、パスはこのSKILL.mdの場所を基準に解決する。

```bash
python3 <このスキルのディレクトリ>/scripts/fetch_pr_diffs.py <PR URL...>
```

`gh` の認証が済んでいない環境では動かないので、失敗したら `gh auth status` を確認するようユーザーに伝える。

- 各URLから owner/repo/PR番号を都度パースするため、対象PRが別リポジトリにまたがっていても動作する
- 出力は一時ディレクトリに `<owner>__<repo>__<number>.md` として保存される (メタデータ + description + diff)
- 取得できなかったPR (権限不足・存在しない・URL不正) は標準エラーに出るので、続行前にユーザーと共有する

### 2. 変更内容の把握

- 出力された各PRのmdファイルを読み、title/descriptionから意図を、diffから実際の変更内容を把握する
- PRが3件以上ある場合は、サブエージェントで各PRを並列に読み込み・要約させ、メインのcontextを圧迫しないようにする
- 対象リポジトリがローカルにある場合は、diffだけでは判断できない箇所 (変更された関数の呼び出し元、既存のバリデーション、画面上のラベル文言) を実際のソースで確認する。**画面ラベルの正確な文言はチェックリストの品質に直結する**ため、フロントエンドのコードやi18nの辞書ファイルから実際の表示文字列を拾う

### 3. ユーザーから見える挙動変化への翻訳

diffの変更を、**QA担当者が画面上で観測できる事実**に置き換える。ここで翻訳できなかった変更は、後段の「開発者に確認を依頼する項目」に回す。

- フロントエンドの変更 → どの画面のどの表示・操作がどう変わるか
- バックエンドのみの変更 → レスポンス内容・エラーメッセージ・処理速度・保存されるデータなど、ユーザーから見て何が変わるか。「画面に変化がない」と結論づける前に、エラー時の表示や一覧の並び順など間接的に見える箇所を疑う
- 設定・環境変数・マイグレーションの変更 → リリース時に必要な作業や、既存データがどう見えるか

### 4. 大項目 (テスト観点のグルーピング) を決める

画面・機能の単位で大項目を切る。PRごとには**分けない**。目安は3〜7個。以下の観点のうち、**今回のdiffが実際に触っているものだけ**を大項目にする。触っていない観点の大項目は作らない。

- 変更された機能そのものの正常系
- 変更された機能の異常系・境界値
- 権限・テナント (ロール違い、他テナントのデータが見えないか)
- 既存機能への影響 (リグレッション)
- 表示・i18n (日英切り替え、表示崩れ、ローディング/エラー表示、レスポンシブ)
- データの整合性 (作成・更新・削除に伴う関連データの状態)

例: diffにロール判定・テナント絞り込みが一切ないなら「権限・テナント」の大項目は作らない。i18nの辞書に手が入っていないなら「表示・i18n」を独立した大項目にはせず、表示崩れの項目だけを他の大項目に混ぜる。

### 5. 境界値・コーナーケースの候補出し

**この工程を省略しない。** 同梱の `references/edge-cases.md` を読んで候補を洗い出す。ただし**全カテゴリを機械的に当てるのではなく、diffにそのカテゴリの「探すサイン」が実際に現れているかを先に判定し、現れたカテゴリだけを当てる**。

- サインが1つも見つからないカテゴリはそのまま飛ばす (例: 外部API呼び出しもファイルアップロードもdiffに無いなら「通信・外部依存の失敗」は当てない)
- 判定に迷ったら当てる側に倒す。ここは候補出しの工程で、絞るのは次の工程の役割

特に重視するのは次の2つの探し方:

- **境界のちょうど内と外**: diffの条件分岐 (`if`・early return・バリデーション・上限値の定数) を見つけたら、その境界の内側と外側の両方を候補にする
- **バリデーションが無い入力経路**: バリデーションが**書かれていない**入力・操作経路を探す。ここが「実装段階で想定されていないケース」の本命なので、見つけたら必ず候補にする

### 6. 選別 (必須 / 任意の振り分け)

**候補をそのまま全部出さない。** ここで絞らないとQA担当者が実施しきれない量になり、結果として全項目が雑に流される。

#### 必須項目数の目安

手順1で取得した各PRのメタデータ行 (`Changed files: N (+A/-D)`) を全PRで合計して規模を決める。テストコード・lockファイル・自動生成物は行数から除く。

| 規模 | 目安 | 必須項目数 |
|------|------|-----------|
| 小 | 変更5ファイル以下 / 増減200行未満 | 15項目前後 |
| 中 | 変更20ファイル以下 / 増減1000行未満 | 25項目前後 |
| 大 | それ以上 | 40項目を**上限** |

#### 振り分けの基準

各候補に「**壊れたときの影響度**」と「**実際に踏まれる確率**」を当て、高いものから必須に詰める。上限に達したら残りは任意に回す。

- **影響度が高い**: データが失われる / 他人・他テナントのデータが見える / 課金・外部通知が誤る / 機能そのものが使えなくなる
- **確率が高い**: 主要な操作フロー上にある / 全ユーザーが通る / 自由記述の入力欄である

影響度と確率がどちらも低いものは任意に回す。

#### 上限に関係なく必須に入れるもの

- 変更された機能の**主要フローの正常系** (これが通らないならリリースできない)
- **権限・テナント境界**の項目 (diffに該当のサインがある場合)
- **データの破壊・不整合**につながる項目 (削除・マイグレーション・一括更新)
- **リリース作業**と**開発者に確認を依頼する項目**

これらを入れて上限を超えるなら、上限ではなくこちらを優先する。超えた分は正常系の派生パターン (同じ操作を別の入り口から行う等) から任意に回す。

### 7. チェックリストの生成

`references/output-format.md` のテンプレートと記述ルールに従って生成する。要点:

- 大項目は `##` 見出し、その直下に**前提** (アカウント・権限・事前データ) を書き、小項目は5列のテーブル (`✓` / `#` / `確認項目` / `再現手順` / `想定事象`) で並べる
- 冒頭に「この変更で何ができるようになるか」「対象PR一覧」「テスト前の準備」を置く
- 必須項目のテーブルの後、末尾に「**時間があれば実施**」セクションを置き、任意に回した項目を同じ5列で並べる
- 画面から判定できない項目は、テーブルに混ぜず末尾の「開発者に確認を依頼する項目」に分ける

### 8. 自己レビュー (品質ゲート)

生成したチェックリストを読み返し、以下をすべて満たすまで直す。

- [ ] 実装用語 (API名・関数名・カラム名・変数名・PR番号) がテーブル内に残っていない
- [ ] 「正常に動作する」「問題なく表示される」のような判定できない想定事象がない
- [ ] 1行に複数の**別々の**確認が詰め込まれていない (同じ境界の内側と外側を1行にまとめたものは除く)
- [ ] ボタン名・メニュー名が実際の画面文言と一致している (推測で書いた箇所が残っていないか)
- [ ] 前提条件だけを読んで、QA担当者が自力でテスト環境を準備できる
- [ ] 必須項目に境界値・コーナーケースが含まれている (すべて「時間があれば実施」に逃がしていない)
- [ ] テーブルのセル内で改行 (`<br>`) を使っていない (Notionで崩れるため)

### 9. 保存

- プロジェクトルートに `release-qa/` ディレクトリがなければ作成する
- `.gitignore` に `release-qa/` が含まれていなければ追記する (誤ってコミットされないようにするため)
- `release-qa/<日付>-<機能名スラッグ>.md` として保存する (例: `release-qa/2026-08-04-workspace-file-upload.md`)
- 保存後、ファイルパスと、大項目ごとの項目数サマリー (必須と任意の内訳、判定した規模) をユーザーに報告する
