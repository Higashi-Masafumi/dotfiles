# Release QA

## 目的

リリースQAを、変更された仕様や画面上の全挙動を細かく確認する工程として扱わない。**リリースによって開発者の想定外の挙動（バグ）が起きないと判断するために、実際のユースケースを通じて高リスクな壊れ方を効率よく検出する。**

内部ではバグ仮説を作るが、成果物はバグ仮説や実装単位を並べたリストにしない。ユーザーが実際に達成したい仕事を大項目にし、その一連の操作で複数の関連リスクをまとめて確認する。

次の条件をすべて満たすこと。

1. **実際のユースケースである**: 大項目が「ユーザーが何を達成するか」を表している
2. **変更との因果がある**: 各確認について「どの変更が、なぜ、どう壊れ得るか」を内部的に説明できる
3. **少数のシナリオに統合されている**: 値・入口・表示箇所ごとに項目を分割せず、一連の仕事として確認する
4. **そのまま再現できる**: 必要な入力データ、プロンプト、アカウント、操作の起点が具体的である
5. **重要な結果だけを判定する**: 処理経路、成果物、内容の整合性など、バグ検出に必要な通過点だけを書く

次のものは目的に含めない。

- 変更された画面・入力・表示パターンの総当たり
- diffの変更箇所と1対1で対応するテスト項目
- 変更と関係しない既存機能の網羅的なリグレッション
- フレームワークや既存の共通処理が保証している挙動の再確認
- 項目数を満たすための正常系、境界値、ブラウザ・端末違いの水増し

## 入力

`$ARGUMENTS` にGitHubのPR URLをスペース区切りまたは改行区切りで受け取る。気になるポイントや利用シーンが一緒に書かれていればそれも使う。

```text
/release-qa https://github.com/neoAI-inc/neo-smart-chat/pull/1234
```

PR URLは必須。1つも渡されなかった場合は実行前にユーザーに確認する。

## 手順

### 1. 気になるポイントと利用シーンをヒアリングする

この工程を飛ばさない。`$ARGUMENTS` に回答がなければ、次をまとめて1回で質問して回答を待つ。

- 今回の変更を使って、ユーザーが実際に達成したい仕事
- 代表的な入力データ・プロンプト・操作と、最終的に得たい成果物や結果
- 実装中に迷った分岐、壊れそうな箇所、過去にバグが起きた周辺
- 壊れた場合に特に困ること（データ消失、権限漏れ、誤通知、主要機能の停止など）
- QA対象外の範囲と、用意できるアカウント・権限・テスト環境の制約

回答は断片的な箇条書きでよい。完璧な回答を求めて往復を重ねない。diff取得は回答待ちと並行してよい。

### 2. diffとPR情報を取得する

同梱の `scripts/fetch_pr_diffs.py` を、このSKILL.mdの場所を基準に解決して実行する。

```bash
python3 <このスキルのディレクトリ>/scripts/fetch_pr_diffs.py <PR URL...>
```

`gh` の認証エラーなら `gh auth status` の確認をユーザーに依頼する。取得できなかったPRがあれば、続行前に共有する。

### 3. 変更と影響経路を把握する

- title・descriptionから変更目的を、diffから実際の変更を把握する
- 条件分岐、状態遷移、入力制約、権限判定、保存・削除、外部連携、共有コンポーネントの変更を優先して読む
- 対象リポジトリがローカルにあれば、変更箇所の呼び出し元、既存バリデーション、画面ラベルをソースで確認する
- PRが3件以上なら各PRの読解をサブエージェントに分担させ、メインで影響経路を統合する

開発者の気になる点に対応する変更を特定する。加えて、開発者が挙げていなくても、diffから判明した高リスクな影響経路は残す。

### 4. バグ仮説を作る

起こり得る壊れ方を、内部的に次の形で整理する。

```text
変更・条件 → 起こり得る想定外挙動 → ユーザーへの影響 → ユースケース内の観測方法
```

優先して仮説化する。

- 主要な仕事が最後まで完了しない
- 意図した処理先・モード・権限で実行されない
- 入力や中間成果物が次の処理へ正しく引き継がれない
- 生成・保存された成果物が開けない、再利用できない、内容が食い違う
- 再読み込みや再訪問によって履歴・状態・成果物が失われる
- 権限やテナントの境界を越えて表示・操作できる
- 二重操作や古い状態によって重複・不整合が起きる

「変更との因果」「ユーザー影響」「ユースケース内の観測方法」のいずれかを説明できないものはQA対象にしない。画面から観測できない高リスク事項は完了報告へ回す。

### 5. 未想定ケースの候補を補う

`references/edge-cases.md` を読み、diffに実際に現れたサインだけを使う。カタログの値やカテゴリを総当たりしない。

- 既存のユースケースに自然に組み込める代表値・状態を1つ選ぶ
- 同じ原因で壊れる入力値や操作入口は増やさない
- 境界値だけの独立項目は、高リスクかつ実際のユースケースでは検出できない場合だけ作る
- 発生確率が低く影響も軽い未想定ケースは落とす

### 6. バグ仮説をユースケースへ統合する

各仮説を「壊れたときの影響度 × 実際に踏まれる確率」で並べ、上位の仮説を検出できる現実的な利用シナリオを選ぶ。1つのシナリオで複数の関連仮説を確認してよい。

大項目は**1つのエンドツーエンドなユーザー目的**にする。たとえば「ファイルを作る」「ファイルをダウンロードする」「内容を確認する」を別々の大項目にせず、「売上分析の結果からグラフを作成」の中の重要な通過点としてまとめる。

| 変更規模 | 大項目となるユースケース数の目安 |
|----------|----------------------------------|
| 小: 主要な利用経路が1つ | 1〜2件 |
| 中: 利用経路や成果物が複数 | 2〜4件 |
| 大: 複数の主要フローや権限境界を含む | 3〜6件 |

件数は目標ではない。より少ないユースケースで高リスクな仮説を検出できるなら、下限を満たす必要はない。各大項目の子チェックは原則2〜4件に絞る。

必ず残すもの:

- リリース目的を確認する代表的なエンドツーエンドの利用シナリオ
- データ消失・権限漏れ・誤課金・誤通知・主要機能停止につながる仮説
- 開発者が気にしている点のうち、具体的な壊れ方を説明できるもの

落とすもの:

- 具体的なバグ仮説がなく、仕様どおり動くことを細かく確認するだけの項目
- 同じ原因を値・入口・画面だけ変えて再確認する項目
- 実際の利用を模しておらず、変更箇所を通すためだけに作った不自然な操作
- 今回のdiffのどの変更で壊れるかを指せない項目
- QA担当者の環境では実行できない項目
- 正しい結果を確定できず、合否を判定できない項目

複数シナリオに共通する履歴保持、再ダウンロード、権限境界などは、各シナリオで繰り返さず、最後に1つの横断項目としてまとめる。

### 7. 未確定事項だけを確認する

次の場合だけ、ユーザーへまとめて1回で質問する。

- 影響度が高いが、実際の利用シーンや正しい期待結果を確定できない
- 高リスク項目の実施に必要な環境を用意できるか不明
- 開発者が気にしている点に対応する変更がdiffに見つからない

高リスクなバグ仮説を追加してよいかは質問しない。回答しても確定しない項目は落とし、残存リスクとして完了報告に書く。

### 8. チェックリストを生成する

`references/output-format.md` に従う。

- 冒頭はタイトル、対象PR、テスト前準備だけにする
- `## QAチェックリスト` の直下へユースケース単位の大項目を `- [ ]` で並べる
- 各大項目の子チェックには、処理経路、成果物、内容の整合性など重要な合格条件だけを書く
- 送信するプロンプトや入力値は、そのままコピーして使える形で子チェックの下に書く
- `前提条件`、`手順`、`期待する結果` の定型ブロックや項目番号を使わない
- 実装用語を使わず、実際の画面ラベルを使う

### 9. 自己レビューする

次をすべて満たすまで修正する。

- [ ] 各大項目が実際のユーザーの仕事を表し、操作部品や実装単位の名前になっていない
- [ ] 各大項目を1回実施すれば、開始から最終成果物まで確認できる
- [ ] 各子チェックが、見逃すと困る具体的なバグの通過点になっている
- [ ] 送信するプロンプト、入力データ、期待する成果物や値が具体的である
- [ ] 同じバグを検出する値違い・入口違い・表示違いが重複していない
- [ ] `手順` と `期待する結果` に分けた冗長な説明がない
- [ ] 複数シナリオに共通する確認が横断項目へ統合されている
- [ ] 実装用語や推測した画面文言が残っていない
- [ ] 項目数を増やすためだけのテストがない

### 10. 保存して報告する

- プロジェクトルートに `release-qa/` がなければ作成する
- `.gitignore` に `release-qa/` がなければ追記する
- `release-qa/<日付>-<機能名スラッグ>.md` として保存する

保存後、次を簡潔に報告する。

- ファイルパス、大項目数、判定した変更規模
- カバーした主要なバグ仮説
- 未確定・環境制約によって残った高リスク事項
- 画面から観測できず、開発者側で確認が必要な事項
- リリース時・リリース後に必要な作業

落とした低リスク候補を1件ずつ列挙しない。判断に影響する除外理由がある場合だけ、カテゴリ単位で伝える。
