# Python Review

## 目的

Pythonバックエンドコードを **コードスタイル** と **DDD / Onion Architecture** の2軸でレビューし、指摘して終わりにせず**その場で修正する**。

## 対象範囲の決め方

`$ARGUMENTS` にファイル・ディレクトリが渡されればそれを対象にする。渡されなかった場合は次の順で決める。

1. コミット前の変更がある → `git diff HEAD` の範囲
2. 変更がない → 直前のセッションで実装・修正したファイル
3. どちらも判断できない → ユーザーに対象を確認する

**レビュー対象は差分ではなくファイル全体で読む。** 差分だけを見ると「既存の同じ責務のメソッドと重複している」「切り出した関数が1箇所でしか呼ばれていない」といった指摘が拾えない。

## レビュー観点

### コードスタイル

- 不要なtry/exceptを行っていないか。raiseされる可能性のないexceptionをcatchしに行こうとしていないか
- early return / early continue になっているか。ネストが深くなっていないか
- クラスにおいて不要にprivate methodを増やしていないか。**複数回利用されないのにメソッドを分けることは可読性を下げるため禁止**
- 再定義不要な変数定義・関数定義を行っていないか。再利用されないのに不用意にprivate関数を作っていないか
- DTOなどの型定義はdataclassではなくPydanticの`BaseModel`を用いているか。Value Objectは`frozen=True`になっているか
- 固定値がメソッド内にハードコードされていないか。クラス変数またはモジュールレベル定数になっているか
- 非自明なインデックスアクセス (`items[2]` 等) に、何にアクセスしているか・なぜそのインデックスかのコメントがあるか

### DDD / Onion Architecture

- ドメイン層がapplication / infrastructure層に依存していないか。**依存の方向は常に内向き**か
- Repository / Gateway のabstractインターフェースがドメイン層に定義され、実装がinfrastructureに置かれているか
- Use Caseがビジネスロジックを持たず、ドメイン層に委譲しているか。Use Caseに条件分岐でビジネスルールが書かれていたらドメインへ移す
- 複数エンティティにまたがるロジックがUse Caseに書かれていないか。Domain Serviceが適切か
- ドメインエラーが汎用的な`ValueError` / `Exception`ではなく、具体的なサブクラスとして定義されているか
- FastAPIのDIが`Depends`で行われ、具象がabstractインターフェースに接続されているか

### 全般

- 不要な後方互換性の担保 (未使用の`_var`リネーム、re-export、`# removed`コメント等) がないか
- 一度しか使わない処理のためのヘルパー関数・ユーティリティ・抽象化を作っていないか
- 仮定の将来要件のための設計になっていないか。現在のタスクに必要な最小限の複雑さか
- 既存に同じ責務を持つ (あるいは包含する) メソッドがあるのに重複実装していないか
- **デッドコードが残っていないか。** 新しい実装や修正はデッドコードを生みやすいので、修正後にも再チェックする

## 手順

1. 対象ファイルを読み、上記3カテゴリの観点で問題点を洗い出す
2. 「既存実装との重複」「呼び出し元が1箇所しかない関数」は、対象ファイルの中だけでは判断できない。**シンボル名でリポジトリ全体を検索して呼び出し元・類似実装を確認してから**判断する
3. 見つけた問題はその場で修正する。ドメイン層へのabstractインターフェース切り出しなど新規ファイルが必要な場合はファイルを作る
4. 修正によって使われなくなったコード・importが残っていないか、修正後にもう一度確認する
5. テストがある場合は実行し、修正が既存の振る舞いを壊していないか確かめる

## 報告

- 修正した内容を `file_path:line` 付きで簡潔に箇条書きする
- **修正しなかった指摘は理由とともに必ず報告する。** 特に「設計判断としてユーザーに確認が必要なもの」「修正範囲が対象外に及ぶもの」は勝手に直さず、指摘として残す
- 問題が見つからなかった場合は、観点ごとに何を確認したのかを1行ずつ書く。「問題ありません」だけで終わらせない
